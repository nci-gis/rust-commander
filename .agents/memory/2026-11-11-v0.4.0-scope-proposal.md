## 1. The test for each item

v0.4.0 is the version people meet first and judge by. An item is in only if it passes
both tests:

1. **It earns its place on the market.** It is the reason to choose xdevcmd (the shell
   bridge, panelize), or something a switcher expects and would miss.
2. **It can be finished properly before the release.** That means tested on the three
   systems, documented, and with no half-done corners.

Anything else waits for 0.5, where launch feedback can steer it. A smaller release done
well is the stable one.

## 3. What "stable" means for 0.4.0 (Q, the bar the release must clear)

1. **No known data-loss or crash bug.** Every open finding from Rounds 014–020 is fixed
   or written down as harmless.
2. **A hand-test matrix, run and recorded** (the owner, with a checklist the agent
   writes):
   - Windows: Windows Terminal with cmd and pwsh, and the old console.
   - macOS: Terminal.app and iTerm2.
   - Linux: GNOME Terminal, kitty, tmux, over SSH.
   - Each runs the same 15-minute script: copy, move, delete, undo, archives, the shell
     bridge, B, C, L, F3/F4, Settings, quit with jobs, Japanese names.
3. **Measured, with budgets**, and each kept by a test where possible:
   - start-up under 150 ms;
   - a 100,000-file directory listed and sorted in under 1 s;
   - idle CPU under 0.5 %;
   - memory flat in the soak test;
   - the binary under 7 MB.
4. **A compatibility promise, written in docs/** ("From 0.4.0"): config keys, CLI flags,
   action names in `[keys]` and the theme-file format. Each changes only with a release
   that reads the old form and says what replaced it.
5. **The parsers that read untrusted input get fuzzed** (cargo-fuzz, a few minutes each,
   in CI later): OSC 7, 9;9 and 133, B's path recogniser, config and theme files, archive
   names.
6. **CI on again for the release**: the pull request into `dev` runs everything, the
   Windows ConPTY tests included.
7. **Docs and README for a first-time reader**:
   - the README gets a 20–30 s GIF, three lines of why, and install in one command each
     (cargo, binstall, Scoop, winget, brew);
   - docs/guide.md is checked against what ships.

## 4. Order and time

A (done) → **B** (1 week) → **C** (1 week) → **L** (2–3 days) → **D** (measure on day
one; 3–4 days, or dropped) → **Q** (1–1.5 weeks, item 21 in it) → **0.4.0-rc.1** (a
GitHub pre-release; a week of the owner's real use; fixes only) → **0.4.0** → packages
(Scoop, winget, brew; the owner's accounts) → **launch** (GIF, Show HN).

That is about 5–6 weeks. Each round still starts with its kickoff review and the owner's
go. No new features after rc.1.

## Added later the same day: themes and look

- The owner asked to drop one near-duplicate theme and to design a distinctive
  `xdevtheme`, with a look that can reach the whole app.
- **Dropped: Night Owl.** Mean CIE Lab distance over the 16 slots: dark~night-owl 13.7
  (the closest pair), catppuccin~tokyo-night 15.4, catppuccin~dracula 18.5.
- **xdevtheme: four directions** were rendered from real frames
  (`XDEVCMD_SCREENSHOT_COLOR=1` with `--screenshot`, new) and shown to the owner as a page:
  A Aurora (teal→violet gradient, rounded), B Signal (ink and one orange, heavy focus
  frame), C Phosphor (green CRT, double frames, zebra), D Paper (warm light, red pen).
  The style knobs in it are simulated: `borders`, `focus_borders`, `gradient`, `cursor`,
  `marker`, `keycaps`, `title`, `shadow`, `zebra`. About 3–4 days of engine work. It was
  G (deferred to 0.5) in §2 above, so it needs the owner's call on 0.4.0 or 0.5.
- **For Q:** a `[theme] name` whose file is missing makes xdevcmd ignore the whole config
  file. A missing theme should fall back to `dark` with a note, not drop every setting.
- **The owner chose A + Pulse ("go")**, the same day: built as `themes/xdevtheme.toml`
  and `themes/xdevtheme-dawn.toml`, with the engine in `src/decor.rs` (the theme file's
  `[style]` table). Most of it is one pass over the drawn frame (`decor::decorate`, the
  terminal panels' screens skipped); frames, notches and shadows are at each block.
  Not built: Neon's bloom, Glass's cards, Borealis's sky and stars (simulated only).
  Binary +48 KB. Still open: whether xdevtheme becomes the default.
- **Neon, Glass and Borealis built too** (owner, same day), as `themes/xdevtheme-neon`,
  `-glass` and `-borealis`. New `[style]` keys: `borders = "none"` (cards), `titles =
  "pill"`, `gradient` as two colours, `gradient_runs = "down"`, `cursor = "pill"`,
  `shadow = "glow"`, `glow`, `sky`, `stars`. The pass skips the terminal panels' screens
  (a program's own box stays a box; render test). Glass's and Borealis's `bar` were
  moved so panel and bar stay apart at 256 colours.
- **Memory "grows when switching themes"**: measured in a pty, 150 switches, RSS flat at
  7.3 MB. The one step (about +2 MB) comes about 2 s after start with no input at all:
  the background threads starting. Not a leak; on Windows not measured.
- **Trimmed to three and made default** (owner, same day: "1 crazy, 1 sáng tạo, 1
  professional"; "xdevtheme làm mặc định"): xdevtheme is now a built-in and the default
  (`theme::DEFAULT`, `Theme::default()`; the old look is `Theme::dark()`, name "dark").
  Neon (crazy) and Glass (creative) stay as files; Dawn and Borealis were dropped.
  A missing or unreadable theme no longer drops the config: the default stands in, the
  status line says so, `--check-config` still exits 1. `XDEVCMD_THEME` overrides the
  name for one run; the test harnesses set it to "dark" so their glyph checks hold.

## The owner's answers, 2026-11-11 (after the Round 021 kickoff)

- **F, remote: deferred, not in 0.4.0.** v0.4.0 is about being stable: no network, no
  telemetry. Later, remote may come "by a safer way, through trusted tools, a network
  mount for example": the OS or a third-party tool (sshfs / SSHFS-Win, rclone mount,
  SMB, NFS) does the network, and xdevcmd sees local paths, so hard rule 2 is untouched.
  - Found while answering: a directory is read on the UI thread (`FilePane::reload` →
    `read`), so a dead or slow mount freezes the screen. Only archives are listed off
    the thread (`opening`, Esc stops). Making listings safe on a slow mount belongs in
    Q, and is what a "remote by mount" story needs first. A docs page on mounting
    (per system) costs nothing and can ship with 0.4.0.
- **Plugins (items 11–13): postponed, low priority.**
- **Panelize, the owner's idea:** a list once made should not be lost. When the user
  opens a file from it and comes back, a key shows the previous list again; a path gone
  since is reported and removed. Alt+F7's results and lists from the history go into
  the same place. Kept in memory (or a temp file). Folded into Round 021's kickoff once
  the owner agrees on the shape.
